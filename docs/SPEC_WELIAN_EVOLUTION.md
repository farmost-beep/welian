# Welian 演化方向补充

> **核心判断：Welian 已经能"感知→决策→交付"，但还不会"复盘→学习→自我修正"。下一步不是加感知源或输出格式，而是把用户每次行动的结果回流到下一轮决策，让系统从"每次都从零开始推荐"变成"越用越懂你这个人和你的关系网"。**

---

## 0. 与 SPEC_WELIAN_NEXT.md 的关系

本文档是 SPEC_WELIAN_NEXT.md v2.1.0 的后续演化方向，不修改 R0-R3 的已有规约。

SPEC_WELIAN_NEXT.md 的核心立场不变：

1. 定位是"关系行动智能体"，不是"关系操作系统"
2. 每周帮用户完成**一件**重要关系行动
3. 用户确认→执行→记录，不做自动触达
4. 关系伦理、数据主权、不自动社交是版本不变量

本文档在以上前提下，补充"闭环"方向的具体规约。

---

## 1. 问题诊断

### 1.1 当前系统是开环的

```
感知 → 决策 → 交付 → ？
                    ↑ 这里断了
```

用户收到建议后，系统不知道：
- 建议是否被采纳（有 adoption 记录，但不知道**为什么**采纳或拒绝）
- 采纳后的**实际效果**如何（联系了，关系变好了吗？）
- 效果如何**回流**到下一轮决策（insight 改了 prompt，但不改候选逻辑）

### 1.2 对照 AI 工作系统七层模型

| 层 | 能力 | Welian 当前 | 成熟度 |
|----|------|------------|--------|
| 信息获取 | 感知采集 | GitHub + 网页URL + 会议拍照 + 名片扫描 + 自然语言记录 | 70% |
| 分析决策 | 候选排序 + Action生成 | selectRelationshipCandidates + buildRelationshipAction | 60% |
| 生产交付 | 建议输出 | Action卡 + 消息草稿 + 周报 + 感知卡 + 会议复盘 | 75% |
| 质量检查 | 产出验证 | 192 vitest + 5 automator + 发布门 | 30% |
| 自动化执行 | Agent闭环 | 定时推送 + 会议→待办 + 感知→Action | 20% |
| 知识沉淀 | 结构化知识 | EvolutionInsight + contact memories + sensor quality | 25% |
| 持续迭代 | 自进化 | 每周self-evolution + adoption rate + metrics | 35% |

**前3层已成体系，后4层是断点。**

## 2. 修正后的演化路线

### 2.1 修正原则

以下方向**明确排除**（与 SPEC_WELIAN_NEXT.md 第594行一致）：

- ❌ 自动采集和自动触达（"联系人活跃→24h推送"不做）
- ❌ 多步任务编排（"重新建立联系"不拆成6步自动执行）
- ❌ 全联系人关系画像（陪伴型关系不做偏好分析）
- ❌ 黑盒自适应（用户不可见的权重调整不做）
- ❌ A/B 实验框架（当前用户量不支持，且与"可解释"原则冲突）

### 2.2 四阶段路线

#### 第一阶段：质量层 — 让系统知道自己产出的质量

**目标：每条建议有依据、可解释、可反馈**

| 动作 | SPEC 依据 | 说明 |
|------|----------|------|
| Action 卡补"为什么是现在" | SPEC 5.3 | 当前有 reason（为什么推荐这个人）和 source.evidence（依据），缺 why_now（为什么是现在这一周） |
| 感知撤销审计日志 | SPEC 7.2 | confirm/reject/delete 时写 audit trail，记录 who/when/what/why |
| 拒绝原因可选采集 | SPEC 8.1 | Action 卡 skip 时可选原因（时机不对/关系描述不准/不想联系），不强制 |
| 产出一致性检查 | SPEC 6.1 | 同一联系人不同入口给出的建议不矛盾 |

**退出门：**
- 每条 Action 包含 reason + why_now + source.evidence
- 感知 confirm/reject/delete 有审计记录
- 用户可对 Action 和 Insight 给出反馈

#### 第二阶段：执行层 — 单步完成验证

**目标：从"推送通知"到"用户主动打开时的即时响应 + 完成验证"**

| 动作 | 说明 |
|------|------|
| 行动结果回检 | 用户标记"已完成"后 7 天，自动检查：是否新增互动记录？如有，标记 action_outcome=effective；如无，标记 action_outcome=no_follow_through |
| 即时响应计算 | 用户打开 dashboard 时，基于最新感知实时计算最优 Action，不是定时推送的缓存 |
| 完成验证反馈 | 回检结果回流到 EvolutionInsight："你标记完成的行动中，X% 在7天内产生了互动记录" |

**不做：**
- 不做自动触发推送（定时推送保留，事件驱动推送不做）
- 不做多步任务编排
- 不做自动发消息

**退出门：**
- 已完成 Action 有 7 天回检结果
- 回检结果出现在 EvolutionInsight 的 evidence 中

#### 第三阶段：知识层 — 仅经营型关系结构化画像

**目标：从散落 memories 到结构化关系知识库**

| 动作 | 说明 |
|------|------|
| 经营型关系画像 | 每个经营型联系人累积 `{沟通偏好, 话题热度, 合作历史, 关系转折点}` |
| Playbook 沉淀 | "这类关系在这种冷却阶段，用这种方式重新联系，成功率 X%" — 仅经营型 |
| 陪伴型关系只记事实 | 陪伴型关系只记录"在场/互动事实"，不做偏好分析、不做画像 |

**伦理边界（不变）：**
- 陪伴型关系不做 ROI、排序、冷却、完成率、产出评估
- 陪伴型关系不生成关系画像
- 所有画像用户可见、可纠正、可删除

**退出门：**
- 经营型联系人有结构化画像
- 陪伴型联系人无画像，只有互动事实
- 用户可查看和纠正画像

#### 第四阶段：迭代层 — 可解释的权重调整

**目标：从每周批量自进化到实时闭环学习**

| 动作 | 说明 |
|------|------|
| 建议→结果闭环 | 记录"推荐了什么 → 用户做了什么 → 7天后关系变化"三元组 |
| 候选权重可解释调整 | 用户可见"我更容易完成有明确话题的建议"，可纠正、可关闭 |
| 模型效果追踪 | 记录每次 LLM 调用的 model_tier + 输出质量 + 用户反馈 |

**不做：**
- 不做黑盒自适应（用户不可见的权重调整）
- 不做 A/B 实验框架（当前用户量不支持）

**退出门：**
- 候选权重调整有用户可见的解释
- 用户可关闭自动调整

## 3. 数据集补充

| 新数据集 | 责任 | 伦理约束 |
|---------|------|---------|
| perception_audit | 感知确认/拒绝/撤销的审计日志 | 只记录操作事实，不记录感知内容本身 |
| action_outcomes | Action 完成后7天回检结果 | 只记录是否有互动记录，不评判关系好坏 |
| contact_profiles | 经营型联系人的结构化画像 | 陪伴型关系不生成画像 |

## 5. 优先级

```
第一阶段（质量层）  ← 现在做，1-2周
第二阶段（执行层）  ← 紧接，2-3周
第三阶段（知识层）  ← 1-2月
第四阶段（迭代层）  ← 持续
```

**理由：质量层是其他三层的基础。不知道产出质量，就无法判断自动化执行是否正确、知识沉淀是否有价值、迭代方向是否对。**

---

## 6. 成功与失败的判定

### 成功

> 用户不需要理解 Welian 的所有功能，只需要在一次互动后留下事实，下一次打开时看到一个有依据、可解释、不过度打扰、可以完成的行动；完成后系统能验证结果，并在下次更懂用户——而且用户能看到"懂了什么"、可以纠正。

### 失败

- 建议有 reason 但没有 why_now，用户不知道"为什么是这周"
- 感知被撤销但没有审计记录，无法追溯
- 系统在"学习"但用户看不到学了什么、无法纠正
- 为了"闭环"而做自动触达，违反用户确认原则
- 对陪伴型关系做了画像或产出评估

---

## 7. 一句话总结

> 不是让系统"越用越聪明"（那是黑盒），而是让系统"越用越**可信**"——每条建议有依据、每个行动有结果验证、每个洞察可纠正、用户始终掌控。
