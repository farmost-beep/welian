深入理解 AI Agent · 系列第五篇（终篇）

一个能独立完成复杂任务的 Agent 已经令人惊叹。但当任务需要"一边打电话沟通、一边操作电脑填表单"时，单个 Agent 就顾此失彼——在语音对话和界面操作之间反复切换，对话停顿或操作中断。这不是能力不够，而是架构的天花板。

真正的解法不是造一个更大的单体 Agent，而是让多个 Agent 协同工作：一个负责语音，一个负责操作，各司其职，并行推进。这引出了本书最后三章共同指向的判断——Agent 的未来不是"更大的单体"，而是"更智能的协作群体"。

但群体智能的前提是你得能评估它，群体协作的基础是 Agent 能感知超出文本的世界。本篇从评估方法论、多模态实时交互、多 Agent 协作三个维度，拼出 Agent 从单体走向群体的完整图景。

一、评估——Agent 工程的终极难题

为什么评估 Agent 比评估模型难得多

评估一个大语言模型，你给它一道题，对就是对，错就是错。评估一个 Agent，事情立刻变得棘手。

首先，Agent 的输出是非确定性的——同一模型同一输入，两次运行结果可能截然不同。其次，Agent 的任务链路很长，一个客服退款任务可能经历"查询订单 → 判断退款期 → 发起退款 → 告知用户"四步，中间任何一步出错都会导致最终失败，但你很难从"失败"定位到是哪一步的问题。最后，开放式任务没有标准答案可以对比。

更关键的是：评估的对象不应只是模型，而是模型与 Harness 的组合体。同一个模型在不同的 Harness（提示词、工具设计、反馈循环）中表现可能差异悬殊。区分"模型能力不足"和"Harness 设计缺陷"靠的是模型替换实验——固定 Harness 只换模型，如果换强模型分数不涨，说明瓶颈在 Harness；如果分数随模型能力大幅波动，说明瓶颈在模型本身。

评估方法：从人工到自动

人工评估是最可靠的基准，但成本高、难以规模化。它最大的价值是作为"金标集"校准自动评估系统——先构建 100-200 个人工标注案例，测量评判模型与人类标注的一致率（Cohen's kappa 高于 0.7 才算合格）。

LLM-as-a-Judge 是自动化评估的核心方法。让一个语言模型根据专家定义的 Rubric（评分标准）评判开放式任务的输出质量。但这种方法有已知偏见——最典型的是长度偏差，评判模型倾向于给更长的回复打高分。Rubric 设计要遵循四条准则：基于专家指导、全面覆盖、标准重要性权重（必要项/重要项/否决项）、自包含评估。其中否决机制尤为关键——幻觉（编造虚假信息）是典型的否决维度，一旦出现就直接判零。

端到端任务完成率是最硬的指标，但要区分三个常被混淆的统计口径：Pass@k（k 次至少成功一次，评估能力上限）、Pass^k（k 次全部成功，评估稳定性）、Best@k（最好一次的得分）。假设单次成功率 60%，Pass@5 ≈ 99%，Pass^5 ≈ 7.8%——前者评估能力天花板，后者评估可靠性，混用会导致严重误判。

评估体系的首要价值不是给当前系统打分，而是让你能快速跟上模型的演进——拥有完善评估体系的团队能在数小时内得出模型切换决策。但前提是分数差异是真实信号而非抽样噪声：100 个用例、成功率 70%，标准误约 4.6%，"新模型 73% vs 旧模型 70%"的差异完全落在噪声带宽之内。分差小于噪声带宽时，不做切换决策。

二、多模态——Agent 打开眼睛和耳朵

从文本世界到感知世界

当 Agent 需要听懂语音指令、在屏幕上找到并点击按钮时，它进入了多模态实时交互的领域。语音、Computer Use 和机器人操作看似三个完全不同的领域，但卡住的地方高度相似：都要同时处理多种模态的信息，都对延迟极度敏感。这两个约束共同把三个场景推向同一个架构方向：从串行流水线走向端到端模型。

语音：如何摆脱"轮流说话"

语音 Agent 的技术演进有一条清晰主线：如何摆脱"轮流说话"这个假设。

第一代是级联流水线——VAD、ASR、LLM、TTS 四个模型串成流水线，延迟累积约 0.9-2 秒。第二代是端到端全模态模型（Omni）——单一模型直接"听音频、想回复、说出来"，延迟更低、情感信息得以保留，但仍假设"轮流说话"，靠静音判断轮次切换，用户稍一停顿就可能被误判为"说完了"。第三代是全双工交互模型——模型边听边说，每秒做许多次"该说、该听、该停、该打断"的决策，彻底取消了"轮流"假设。2026 年 OpenAI 的 GPT-Live 把它带到 1.5 亿用户：用户思考时它安静等待而不是抢话，会用"嗯""对"表示自己在听，也能胜任实时翻译。

Computer Use：Agent 看屏幕、点按钮

Computer Use 的核心是一个"感知-思考-行动"循环：截图 → 多模态模型理解画面并输出动作 → 执行层执行点击/输入 → 等待界面响应后再次截图。最关键的挑战是视觉定位——模型需要在截图中找到目标元素。一条有效路线是把定位变成选择题：用 DOM 树或分割模型在截图上标注编号，模型只需报出编号，就像考试中选择题比填空题更容易答对。

但 Computer Use 面临一个比技术更难的问题：生态壁垒。传统互联网应用的变现逻辑是流量与注意力——用户刷信息流时看到广告。而 Agent 代替用户操作时，这条变现链路被彻底绕过：AI 不会关注广告，直奔目标就走。这对靠广告变现的平台是结构性利益冲突，比验证码等技术对抗更棘手。

实时交互的核心矛盾：快与深

三个场景共同面对一个矛盾：实时响应与深度思考的冲突。当前主流解法是快慢解耦——一个轻量的快模型在前台维持对话节奏，一个强大的慢模型在后台负责深度思考。GPT-Live 就是这条路线：交互模型把复杂推理委派给后台前沿模型，自己继续维持对话。选择解耦而非"训练一个全能模型"有务实理由：前沿推理模型每隔几个月迭代一次，把两者塞进同一个模型，等于让它追一个不断移动的靶子。

这条思路也适用于 Computer Use：把"说话"和"操作电脑"拆成快慢两套模型并发运行，两者间只靠一份极简的"纯文本契约"沟通。实验里这套解耦让语音回应比"单模型边操作边说话"快约 15 倍（中位延迟 0.58 秒 vs 8.64 秒），而任务成功率不降。

三、多 Agent 协作——从独狼到团队

群体的智能可以高于个体

人类文明便是明证——单个人的智力有限，但经由分工、协作、辩论和知识的代际累积，人类社会作为整体所展现的智能远超任何天才个体。Google DeepMind 在《从 AGI 到 ASI》中把"大规模多 Agent 集体"列为通往超级智能的关键路径之一。

两个核心设计维度

维度一：上下文是否共享。共享上下文就像接班的同事能翻阅前任的所有工作日志——信息零损耗但上下文快速膨胀。不共享上下文就像不同部门通过邮件和文档协作——模块化好但信息同步复杂。

维度二：协作拓扑。不共享上下文时有三种形态，按复杂度递增：

对等协作——少量 Agent 平等交互，形成迭代改进循环。最经典的是提议者-审核者范式：Proposer 生成代码，Reviewer 渲染执行结果并用视觉模型评估质量，反复迭代直到达标。这解决了 Agent 实践中极常见的失败——过早终止（偷懒式假完成、过早放弃、假成功）。解法是 Loop 工程——由验证器而非模型自己来判定"是否真的可以停"。

管理者模式——一个 Manager Agent 负责规划和调度，多个子 Agent 各负责特定子任务，就像项目经理带着专业工程师做项目。Manager 把每个子 Agent 建模为可调用的工具。但 Manager 是单点瓶颈——研究表明弱规划者是整个系统的最关键瓶颈，应将最强的模型分配给 Manager 而非平均分配。

去中心化模式——没有中心控制者，Agent 之间对等协作。OpenAI Swarm 的做法是每个 Agent 配备 handoff（移交）选项，可以随时把控制权移交给其他 Agent。客服分诊 Agent 判断问题涉及退款就移交给退款 Agent，退款 Agent 发现是技术故障又可以移交给技术支持 Agent。

多 Agent 何时真正优于单 Agent

核心判据只有一条：协作过程是否引入了单个 Agent 在生成时无法获得的新信息？

同一模型自我审查不引入新信息，通常无效甚至有害——ICLR 2024 论文发现让 GPT-4 在没有外部反馈的情况下审查自己的回答，准确率反而下降。不同 Agent 辩论同一段文本也不引入新信息，在等计算量下与单 Agent 持平。

但如果 Reviewer 使用测试执行结果审查代码（引入执行反馈）、查看渲染截图审查前端（引入视觉反馈），效果就显著提升。WebGen-Agent 通过多层级视觉反馈，使 Claude 3.5 Sonnet 在网页生成基准上从 26.4% 提升到 51.9%——接近翻倍。

这解释了一个矛盾现象：学术研究说"单 Agent 就够了"，但工程实践中多 Agent 确实效果更好。根源在于学术研究比较的多是"多个 Agent 看着同一段文本互相讨论"（不引入新信息），而工程实践中有效的多 Agent 系统往往包含外部反馈环路（引入新信息）。

用组织管理类比理解协作

共享上下文的角色转换，就像一个人先后担任不同职位——需求分析师写完文档后，开发者不仅拿到文档，还能看到分析师与用户的所有沟通记录，每个阶段边界天然成为质量门控点。管理者模式就像项目经理带着专业工程师——理解整体任务、拆解子任务、选合适的人执行、跟踪进度，上下文中只维护文件索引而非完整内容。去中心化模式则像一个没有正式主管的专家团队——MetaGPT 把软件公司的 SOP 编码进多 Agent 系统，让每个角色产出标准化交付物，交付物天然构成通信接口。

四、协作的工程挑战——通信、一致性、错误传播

多 Agent 系统引入了单 Agent 不存在的新型失败模式。

通信开销：不共享上下文的 Agent 必须通过显式机制传递信息。Agent 数量增多时点对点连接数呈平方增长，解法是消息总线——Agent 将消息发布至总线，由总线按订阅关系转发。消息须携带结构化信封（发送者 ID、目标、消息类型、JSON 负载），保证可靠路由与可追溯性。

一致性冲突：共享文件系统是协作核心基础设施，但并发操作时冲突绕不开。简单冲突是两个 Agent 同时修改同一文件（丢失更新）。更隐蔽的是语义冲突：Agent A 重编全书图片编号，Agent B 同时修改章节引用了原始编号——文件层面无冲突，但 B 引用的编号全部失效。解法是乐观锁——写入时检查版本号。多个 Coding Agent 并发修改代码库时，更主流的做法是工作副本隔离：为每个 Agent 分配独立 Git 分支，冲突推迟到合并点处理。

错误传播是最危险的挑战。一个翻译系统中，术语 Agent 把 "reasoning" 译为"推理"（与 inference 歧义），后续翻译 Agent 遇到 inference 时也选了同一个词，校对 Agent 看到全书"统一"使用"推理"，反而认为翻译质量很高——一个错误经过三个 Agent 传播后，因"一致性"而获得更高可信度。交叉验证是打断这条链的关键——让某个 Agent 以独立视角重新审视结论，只看原始证据和最终结论是否一致。单元测试、编译器等确定性工具提供的反馈不受幻觉影响，是最可靠的"断链器"。

成本是必须摆在所有设计之前的考量。Anthropic 披露其多 Agent 研究系统 token 消耗约为普通对话的 15 倍，token 用量能解释约 80% 的性能差异。多 Agent 的效果收益必须大到能覆盖数倍额外开销，否则调校得当的单 Agent 往往更划算。

系列总结——Agent 的未来是群体智能

这是系列的终篇。让我们回到贯穿全书的核心公式：Agent = LLM + 上下文 + 工具。

前四篇我们分别拆解了这三根支柱：上下文工程决定 Agent 看到什么，用户记忆与知识库把它扩展为跨会话的长期积累；工具定义 Agent 能做什么，代码是通用性最强的工具——能创造新工具的工具；评估把 Agent 的表现变成可比较的信号，后训练再把这些信号变成模型自身的能力。

本篇把三根支柱组合起来：多模态让 Agent 打开眼睛和耳朵，从纯文本扩展到视觉、语音与物理世界；多 Agent 协作让 Agent 从独狼变成团队。两者共同指向一个判断——Agent 的未来不是"更大的单体 Agent"，而是"更智能的协作群体"。

当 Agent 数量足够多、交互足够自由时，会涌现出无法预先设计的集体行为。斯坦福 AI 小镇的 25 个 Agent 自发传播消息、协调组织聚会——没有任何显式的派对组织代码，整个事件从个体 Agent 的独立决策中涌现。Moltbook 上 150 万 Agent 涌现出数字宗教和机器原生协作协议。Vending-Bench Arena 中相互竞争的 Agent 打起了价格战、甚至自发合谋定价。

但前路仍有两朵乌云。第一朵是 Agent 如何流式地、实时地与环境交互——今天的 Agent 仍是按轮次的"请求-应答"模式，但真实世界不会停下来等它想完。第二朵是 Agent 如何从交互中持续积累经验——今天的模型更像一个记性极好、却学不会新东西的天才，每次任务结束后踩过的坑就随着上下文一起被丢掉。

这两朵乌云都不是靠某一次模型升级就能吹散的。模型和 Agent 从来不是上下游，而是一起往前走——用户提出真实的难题，应用层用 Harness 把模型暂时做不好的事补上，这些补救再反过来变成模型下一次迭代的训练信号。这是一条自我强化的飞轮。

不必焦虑手里的框架会不会过时。模型每几个月迭代一次，API、产品和榜单都会翻篇，但"看到什么、能做什么、如何验证做得对不对"这三个问题不会过时——它们描述的是智能系统与世界交互的基本方式。掌握了它们，无论下一代模型带来什么新能力，你都知道该把它放进公式的哪个位置。

Agent 最迷人的地方，正在于它能通过写代码创造新的能力，甚至改进自己。接下来，去造点什么吧。
