# Agent 的本质：从 LLM 到自主行动者

> 深入理解 AI Agent · 第 1 篇（共 5 篇）
> 基于李博杰著《深入理解 AI Agent》第 1 章

---

你让 AI 帮你订一张机票。它没有直接回答"以下是订票步骤"，而是打开浏览器，搜索航班，比对价格，发现最便宜的需要转机，于是主动问你："可以接受转机吗？"你说不要。它调整搜索条件，找到直飞票，调用支付接口下单，把确认信息发到你手机上。

整个过程没有人一步步指挥它。它自己规划、自己执行、自己纠错。

这不是聊天机器人，这是 AI Agent。

过去两年，从 Cursor 写代码到 Manus 操控浏览器，从 Deep Research 到 Pine AI 替你打电话协商账单——一类全新的 AI 产品正在涌现。它们不再是"你问一句、答一句"的被动对话，而是能自主规划步骤、调用工具完成任务、根据结果调整策略的智能系统。

**AI Agent 正在从"回答问题"跃迁到"完成任务"。** 我们不再只是向 AI 提问，而是让 AI 替我们行动。这篇文章拆解 Agent 的内核。

---

## 一、Agent 的三要素：大脑、眼睛与手脚

理解 Agent，从一个简洁的公式开始：**Agent = LLM + 上下文 + 工具**，更直观的说法是 **Agent = 大脑 + 眼睛 + 手脚**。

**LLM 是大脑。** 它是决策内核——理解意图、思考规划、做出判断。能力来自预训练积累的世界知识和后训练固化的决策策略。收到请求后，它先解析真实意图（用户说的往往不是他真正想要的），再拆解任务，执行过程中持续判断：下一步做什么、调哪个工具、传什么参数。

**上下文是眼睛。** 它是 Agent 在每个决策点能看到的全部信息——环境信息、用户记忆、领域知识、自身状态和任务进展。从 API 视角看，上下文由五部分构成：系统提示词（岗位说明书）、工具定义（能力清单）、用户消息（任务输入）、模型回复（之前的思考与行动）、工具执行结果（上一步的反馈）。前两项是静态前缀，后三项随交互增长。

**工具是手脚。** 它是 Agent 能做的所有事情的集合，按交互方向分为五类：感知工具（搜索、文件系统、数据库——获取信息）、执行工具（代码执行、系统命令——改变世界）、协作工具（委托子 Agent、请求人类确认——分工合作）、事件触发工具（收到邮件、定时回调——被外部驱动启动）、用户沟通工具（发消息、打电话——主动联系用户）。没有工具，Agent 只能"纸上谈兵"。

这三者缺一不可。书中用消融实验验证了这一点：去掉工具定义，Agent 完全丧失行动能力；去掉工具执行结果，陷入无限循环；去掉思考过程，前后决策互相矛盾；去掉历史消息，Agent 失忆，从头重复已完成步骤。**每个组件的作用都有实验证据支撑。**

这里有一个设计哲学：工具应尽量通用。与其设计专用计算器，不如提供 Python 代码解释器加安全沙盒；与其设计记录工作日志的工具，不如提供文件读写加虚拟文件系统。**Agent 的能力边界不是开发者预设的，而是模型在运行时自主探索出来的**——这是它区别于传统软件的根本特征。

## 二、ReAct 循环：Agent 的心跳

三要素就位后，它们如何协同工作？答案是 ReAct 循环——Agent 的心跳。

ReAct（Reasoning + Acting）实际循环包含三个环节：**想 → 做 → 看 → 想 → 做 → 看……** 不断重复，直到任务完成。

用做饭来类比：你先想"今晚做什么菜"（Reasoning），打开冰箱看食材（Acting），发现鸡蛋快过期了（Observing），决定做番茄炒蛋（Reasoning），切番茄打鸡蛋（Acting），发现盐放多了（Observing），加点糖中和（Acting）……你不是一次性规划好所有步骤然后机械执行，而是每步都根据上一步结果调整。这就是 ReAct 的精髓——**思考和行动交替进行。**

书中用一个多币种收入汇总的例子展示这个循环：

- **第 1 轮**：用户说"计算年度总收入：Q1 $2.5M, Q2 €2.1M, Q3 £1.8M"。Agent 思考"需要把 EUR 和 GBP 转换为 USD"，并行调用货币转换工具。
- **第 2 轮**：看到转换结果，调用代码解释器汇总计算。
- **第 3 轮**：生成最终回答："年度总收入 $7,061,089.71。"

3 次迭代，4 次工具调用，完成了一个多步骤任务。

这个设计有一个精妙的特性：**上下文的累积性**。每次 LLM 调用都能看到完整轨迹（trajectory）——从用户第一条消息到最近一次工具结果，全部历历在目。这让 Agent 始终保持全局认知。

用公式表达：**Agent 的上下文 = 静态前缀（系统提示词 + 工具定义）+ 轨迹（不断增长的消息历史）**。每次响应又追加到轨迹中——一个自我丰富的上下文。

**ReAct 循环揭示了一个本质区别：普通 LLM 对话是"一次生成"，Agent 是"迭代推进"。** 前者像考试时一次性写答案，后者像解题时边算边检查边调整。这正是 Agent 能完成复杂多步骤任务的根本原因。

## 三、Harness 工程：模型之外的护城河

ReAct 循环能跑起来，但能跑的 Demo 和可靠的产品之间有巨大鸿沟。模型可能产生幻觉、选错工具、遇到错误无法自我恢复——这些正是 Harness 工程要解决的。

**Harness 是什么？** 这个词原指马具——套在马身上的缰绳与挽具，不是限制马的奔跑，而是把力量引导到正确方向。模型是那匹强大但不可预测的马，Harness 是把它的能力引导成可靠任务执行的工程外壳。

**Agent = LLM + [上下文 + 工具 + 约束 + 验证 + 纠正] = Model + Harness**

最小可工作的 Agent 只需 LLM、上下文与工具（Demo 视角）；要在生产环境长期可靠运转，还需约束、验证、纠正三层外壳（生产视角）。上下文与工具让 Agent"能做事"，约束、验证与纠正让 Agent"不做错事"。

用一个退款的例子感受 Harness 的价值。用户让 Agent 退掉 3 天前的订单：

- **没有 Harness**：模型看不到退款政策（缺上下文），不知道调哪个 API（缺工具），编造退款结果回复用户（缺验证），用户发现退款没发生（缺纠正）。
- **有了 Harness**：系统提示词写明 7 天退款政策（上下文），Agent 调用 query_order 和 process_refund 工具（工具），框架校验退款金额不超订单金额（约束），校验数据库确认退款成功（验证），API 超时自动重试（纠正）。

**同一个模型，有无 Harness，结果天壤之别。**

### Harness 的五个功能

| 功能 | 一句话职责 | 实际例子 |
|------|-----------|---------|
| **上下文管理** | 为模型提供感知信息 | 系统提示词、知识库、Agent 状态栏 |
| **工具调用** | 为模型提供行动手段 | MCP 工具、代码解释器、搜索工具 |
| **循环控制** | 管理推理-行动的迭代与退出 | 最大轮次限制、完成检测、熔断机制 |
| **状态管理** | 追踪执行进展与上下文压缩 | 多层上下文压缩、流程状态追踪 |
| **错误处理** | 约束 + 验证 + 纠正的闭环 | 静默重试、接续生成、失败回退到人工 |

五个功能构成闭环：上下文与工具支撑决策，约束预防错误，验证发现偏差，纠正闭合循环。缺少任何一环，系统都会出现可靠性缺口。

以 Claude Code 为例，Harness 中绝大部分代码都是约束、验证与纠正，而非工具本身——工具（文件读写、命令执行）只是一小部分，围绕工具构建的保障机制才是核心：上下文压缩、权限分类、熔断器（错误连续发生时自动"断电"）、错误恢复（捕获异常、回滚、重试或交还人类）。

### 从提示工程到 Loop 工程：范式演进

回顾 AI 应用工程的发展，能看到一条清晰的演进弧线：软件工程 → 提示工程（优化自然语言指令）→ 上下文工程（管理模型能看到的所有信息）→ Harness 工程（扩展到约束、验证、反馈循环和错误恢复）→ Loop 工程（扩展到跨轮次的持续自主运转）。

这五个阶段层层包含：提示工程 ⊂ 上下文工程 ⊂ Harness 工程 ⊂ Loop 工程，每层都在前一层基础上扩展关注范围。

**当模型能力越来越接近、不再是决定性差异因素时，竞争优势就转移到了模型之外的工程实践。** LangChain 的 Coding Agent 在 Terminal Bench 2.0 上从 52.8% 提升到 66.5%（从 30 名外跃至前 5），改变的不是模型，而是 Harness：让 Agent 自动检查执行结果、检测重复循环、优化思考策略。OpenAI 工程团队也分享了类似经验：3 名工程师 5 个月完成约百万行代码和近 1500 个 PR，达到传统速度约 10 倍。**效率的背后不是模型有多强，而是 Harness 做对了。**

### 一个无法回避的深层问题

如果模型持续变强，今天这些 Harness 会不会被模型"吃掉"？Rich Sutton 在《苦涩的教训》中回顾了 AI 七十年间反复上演的一幕：研究者一次次把对领域的理解编码进系统，短期见效，长期却总输给能随算力和数据规模持续扩展的通用方法。

书中的立场是八个字：**方向认同，节奏务实。** 方向上，模型会持续吃掉 Harness——工具调用、长程规划都曾靠外部编排，如今已是模型原生能力。但节奏上，这个"吃"远比直觉慢：训练以月计，模型无法一次内化真实业务中所有约束与偏好。**模型此刻的能力边界，就是 Harness 此刻的价值所在。**

## 四、编排模式：从工作流到自主的光谱

Harness 解决了"可靠地做事"的问题，但还有一个前置决策：**用什么方式组织 LLM 调用、工具和数据流？** 这就是编排模式——一条光谱，两端分别是工作流和自主 Agent。

### 工作流：确定性的编排

工作流（Workflow）通过预定义代码路径编排 LLM 和工具。执行路径是确定性的——每步做什么、下一步去哪，都是代码写死的，LLM 只在每个节点内部负责理解和生成。

以订机票为例，工作流设计为四个固定节点：核实身份 → 搜索航班 → 完成付款 → 确认预订。节点内部可以用 LLM，但节点间流转是代码固定的——系统不会在付款前去预订座位。

工作流有两个核心优势：**严格的流程控制**（业务规则通过代码强制执行）和**安全性**（执行路径确定，提示注入最多影响当前节点）。局限是**缺乏变通性**——出现预设未覆盖的情况时，只能走异常分支或交还人类。

### 自主 Agent：动态的决策

自主 Agent 与工作流的核心区别在于：**执行路径不是预先定义的，而是 Agent 根据环境反馈实时决定的。**

仍以订机票为例：自主 Agent 不需要预定义节点。用户说"帮我订下周三去上海的机票"，Agent 自行搜索航班，发现需要登录，先核实身份，再搜索，发现最便宜的需转机，主动询问用户是否接受，用户说不要，Agent 调整搜索条件……

从实现角度看，自主 Agent 本质上就是在循环中使用工具的 LLM——正是 ReAct 循环。退出条件包括：调用最终输出工具、无工具调用返回、达到最大轮次、错误超限。

自主 Agent 特别适合开放式问题——难以预测步骤数量的任务，如 Coding Agent 修复 GitHub Issue、Computer Use 操作界面、迭代搜索的研究任务。但自主性也带来更高成本和复合错误风险，部署时必须在沙盒中测试，设置护栏，在关键决策点加入人机协作。

### 不是非此即彼

实践中，工作流和自主 Agent 并非二选一。很多成熟系统混合使用：**关键合规流程用工作流确保可靠性，灵活决策部分切换到自主模式。**

Anthropic 与数十个团队合作的经验总结出一条原则：**从简单到复杂。** 优化提示词能解决就不要引入 Agent；可清晰分解为固定子任务时用工作流；只有需要动态决策和灵活路径时才用自主 Agent。

## 五、护栏与选型：Agent 工程的现实约束

### 护栏：分层防御的底线思维

光能做事还不够，还要做得对、做得安全。护栏（Guardrails）是 Harness 中"约束、验证与纠正"的核心实现，构成 Agent 行为安全可控的分层防线。

按防护位置分为三类：

- **输入侧**：请求到达 Agent 前拦截。相关性分类器标记偏离主题的查询，安全分类器检测越狱和提示注入，内容审核标记有害输入，基于规则的保护用黑名单、正则过滤器防范已知威胁。
- **执行侧**：工具调用时验证。核心是工具风险评级——根据操作是否可逆、权限等级、财务影响标注低/中/高风险，高风险操作需额外审查或人工确认。
- **输出侧**：响应返回用户前检查。PII 过滤器审查个人身份信息，输出验证确保回复与品牌价值一致。

单个护栏不足以提供充分保护，但多个护栏组合使用，就能构建出有韧性的系统。**安全不是上线前打的补丁，而是从第一行代码就要考虑的架构问题。**

人工干预（Human in the loop）是另一个关键保护措施，在两种情况触发：超过失败阈值（重试超限）和高风险操作（敏感、不可逆操作需人工监督）。

### 如何选择模型：不是越大越好

模型是 Agent 的智能基座，选对模型往往比优化提示词更有效。模型迭代极快，与其追逐版本，不如掌握方向。

**场景匹配最重要。** Claude 在复杂推理、编程和工具调用方面突出；Gemini 拥有超长上下文和多模态能力；GPT/o 系列各方面均衡。国内模型中，豆包延迟极低，Kimi 的 Agent 能力较强，Qwen 和 DeepSeek 等开源模型在成本和可定制性上有优势。不要只看排行榜，要在自己任务上评估。

两个易被忽视的维度：**输出速度**（Agent 多轮推理，每轮慢 2 秒，20 轮就多等 40 秒）和**多模态能力**（需理解图片、音频、视频时是硬性要求）。涉及多步思考或动态决策的 Agent，必须选支持思考（Reasoning）的模型。

## 结语：上下文是 Agent 的灵魂

回到那个公式：**Agent = LLM + 上下文 + 工具。**

三要素中，LLM 是大脑，工具是手脚，但上下文——那双眼睛——才是决定因素。消融实验已证明：缺失任何一个上下文组件，Agent 的决策能力都会严重退化。Agent 只能基于它看到的信息做决策。

当模型能力日趋同质化，当工具生态逐渐标准化（MCP 协议正在让工具接入变得像安装插件），**上下文工程将成为 Agent 系统真正的差异化所在。**

下一篇，我们深入 Harness 中最核心的组件——上下文工程：如何设计系统提示词，如何管理不断增长的轨迹，如何在有限的上下文窗口里塞入最有价值的信息，如何防止提示注入窃取系统提示。这是 Agent 工程中最精细的一层。
